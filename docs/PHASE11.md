# Phase 11: bounded RAG quality and offline evaluation

Phase 11 keeps PostgreSQL+pgvector and SQL owner filtering. Retrieval fetches a small vector candidate pool (up to 30 by default; maximum 40) **after filtering by owner in the SQL query**. A deterministic small cosine-plus-lexical score reranks, a configurable optional similarity threshold filters, and normalized duplicate chunk text is suppressed. Ties are broken by score, similarity, document ID, chunk index and chunk ID. Results stay bounded to 10; PostgreSQL integration tests separately check cross-user isolation and SQL-shape tests assert owner predicates and candidate caps.

RAG packs at most 10 retrieved chunks and 800 text characters per chunk into a 6,000-character context by default. Response source references name **only chunks actually included**. Empty retrieval, insufficient context or blank answer produces explicit insufficient evidence. The source list is provenance of supplied context, not a factual guarantee for arbitrary external-model output; human review is still needed. Agent document-search decisions with no evidence cannot be classified as grounded.

The small version-controlled offline suite covers relevant retrieval, source presence, answer evidence signals, insufficient evidence, duplicate suppression, threshold, owner-scope SQL predicate, valid and invalid tools, bounded agent execution, safe provider failure, simulated stream order/terminal status, stream failure safety and output cap. `METRIC rag_pass_rate`, `tool_pass_rate`, `agent_pass_rate` and `stream_pass_rate` are **fixture case pass fractions**, not estimates of real-world hit rate or model factuality. No paid calls, live LLM judge or secret-bearing trace is used. CI runs the evaluation runner through pytest; it can also be run directly with `python evaluation/runner/run_evals.py` from the repository root.

Limitations: lexical overlap is small and English-oriented; the default similarity floor is -1 to preserve Phase 0–8 behavior. Tune it on representative owned documents. Phase 11 is implemented on PR #11 and considered CI-verified only when both workflows pass on the final branch HEAD. The source UI already presents filename, chunk index and similarity; no broad redesign is needed. Nothing here constitutes an actual cloud deployment.
